## Objective

The prebuilt linux.bin (OpenSBI+Linux BBL, from OpenXiangShan/ready-to-run) is the boot image — `--raw-cpt --generic-rv-cpt=linux.bin` boots it directly with no restorer, no disk-image, no toolchain. --mem-type SimpleMemory is used because DRAMsim3 is not built into this RISCV config.

Phase A — single-core boot smoke: download linux.bin, run `build/RISCV/gem5.opt configs/example/kmhv2_chi_6x4_hnf.py --raw-cpt --generic-rv-cpt=ready-to-run/linux.bin --num-cpus 1 --mem-type SimpleMemory`, confirm Linux boots (console shows Linux/Hello) with no tick-0 panic. Phase B — fix the DuelingMonitor 64-bit id overflow (src/mem/cache/tags/dueling.cc:47, `popCount(id) != 1` panic) so 16-core boot advances past tick 0. The fix is at the implementer's discretion (widen the dueling id space, reduce dueling-monitor instances, or change the L2 replacement policy) as long as 16-core no longer panics at tick 0. Rebuild gem5.opt after the fix.

Phase Final — 16-core boot + checkpoint create + restore verify: run the 16-core config with linux.bin + `--take-checkpoints=<tick>` (tick chosen after Linux boot, observed in phase A) to create a checkpoint under m5out; then restore from that checkpoint (`-r 1 --checkpoint-dir=...`) and confirm the simulation resumes and advances ticks beyond the checkpoint point without panic. If restore hangs/crashes due to CHI serialize gaps (the prior goal's serialize was field-coverage-only — queue CONTENTS / in-flight flits were not preserved, and only HomeNodeFull implements Drainable::drain), complete the MINIMAL serialize/drain work needed for restore to advance past the checkpoint — bounded to making restore resume, NOT full flit-content fidelity.
